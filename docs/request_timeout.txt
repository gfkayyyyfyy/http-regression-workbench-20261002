请求超时配置说明（timeout_seconds）
=====================================

本文说明用例中可选的 timeout_seconds 配置如何影响请求执行与报告结果，
供逐项核对。README.md 目前仍将超时描述为"固定 3 秒"，那只是在用例
省略该配置时的行为；源码实际支持显式配置，规则如下。本文只做行为
说明，不改动产品代码与 README；serve 与 run 两个入口保持现有形式
（api_workbench/cli.py 的 main()，第 11-30 行）。

涉及源码位置（均可直接打开核对）
--------------------------------

- api_workbench/runner.py
  - REQUEST_TIMEOUT = 3.0（第 12 行）：默认超时常量。
  - load_case(path)（第 77-210 行）：用例加载与校验；timeout_seconds
    的解析与校验在第 138-157 行，解析结果放入返回字典的
    "timeout_seconds" 键（第 208 行）。
  - execute(case)（第 272-350 行）：发送唯一一次 GET；超时在第
    284-288 行通过 HTTPConnection(timeout=...) 生效，超时/连接异常
    的捕获在第 295-298 行，请求失败的结果取值在第 302-309 行计算。
  - _report(...)（第 213-242 行）：唯一的报告组装函数，成功、断言
    失败、invalid_response、request_failed 四种结果共用同一字段
    结构；execute 末尾（第 341-350 行）统一调用并计算退出码。
  - run_case(path)（第 353-370 行）：CaseError 的处理（打印到
    stderr、返回退出码 2）在第 356-358 行；报告输出在第 360-369 行。
- api_workbench/cli.py：main() 中 run 子命令调用 run_case
  （第 27-28 行），无其他超时相关逻辑。

一、配置取值规则（load_case，runner.py 第 138-157 行）
-------------------------------------------------------

1. 省略 timeout_seconds 键：沿用默认三秒。load_case 先把局部变量
   timeout_seconds 置为 REQUEST_TIMEOUT（第 141 行），键不存在时
   直接使用，因此省略时生效值为 3.0 秒。

2. 显式提供时，只接受 0.1 至 30 秒（含两端）的有限 JSON 数字，
   整数与小数均可（如 0.1、0.5、1、30）。校验分两步：
   - 类型检查（第 145-151 行）：必须是 int 或 float，且显式排除
     布尔（bool 是 int 的子类，需单独判断）；
   - 区间检查（第 153-156 行）：必须满足 0.1 <= 值 <= 30。NaN 与
     ±Infinity 无法通过区间比较，在此一并被拒绝。
   通过后统一转为 float（第 157 行）。

3. 以下取值全部属于用例错误，不做类型转换、不回退默认值：
   - 布尔：true、false；
   - 字符串：如 "1"；
   - null；
   - 数组、对象；
   - 越界数字：0、负数（如 -1、-0.5）、0.09、30.1；
   - 非有限数字：未加引号的 NaN、Infinity、-Infinity（非标准 JSON
     字面量，json 默认解析为 nan/inf 后被区间检查拒绝）。

4. 非法配置的后果（与 README 中其他用例错误一致）：
   - load_case 抛出 CaseError（runner.py 第 148-151、154-156 行，
     错误消息均含 "timeout_seconds"）；
   - run_case 捕获后向 stderr 打印 "api_workbench: <原因>" 并返回
     退出码 2（runner.py 第 356-358 行）；
   - stdout 为空，stderr 以 "api_workbench:" 开头并提及
     timeout_seconds，不出现 Traceback；
   - 校验发生在 urlsplit 与任何网络操作之前（load_case 在第 159 行
     之后才开始解析 URL），因此不发送任何请求。

二、超时的作用范围（execute，runner.py 第 272-300 行）
------------------------------------------------------

1. timeout_seconds 限制的是每次网络阻塞等待的上限，不是整次执行的
   累计截止时间。execute 把它传给
   HTTPConnection(host, port, timeout=case.get("timeout_seconds",
   REQUEST_TIMEOUT))（第 284-288 行），即底层套接字的超时；连接
   建立、等待响应头、读取正文的每次阻塞调用各自受它约束，多次等待
   之间不累加、没有总预算。

2. 等待响应头与等待响应正文都受它影响：connection.getresponse()
   （第 292 行，等待响应头）与 response.read()（第 293 行，按
   Content-Length 读取正文）使用同一个连接超时。

3. 正文读取未完成时，不会先用已经收到的状态码生成成功检查。
   status 变量在第 294 行才赋值，位于 response.read() 之后；只要
   第 291-294 行中任何一步抛出 socket.timeout / TimeoutError /
   OSError / HTTPException，都进入第 295-298 行的 except 分支，
   把 status 置为 None，随后在第 302-309 行按请求失败计算各项
   取值——即使响应头（含状态码 200）已经收到，也整体按请求失败
   处理，不进入后面的状态码比较与字段检查（第 311 行起），也不会
   归为 invalid_response。报告由 execute 末尾统一的 _report 调用
   （第 341-350 行）生成，退出码为 1。

4. 请求失败报告的固定形状（取值在 execute 第 302-309 行计算，
   结构由 _report 第 213-242 行定义）：
   - error 为 "request_failed"；
   - status_check.actual 与 field_check.actual 均为 null；
   - field_check.present 为 null（响应无法用于字段检查，既不能
     确认键存在也不能确认缺失）；
   - 顶层及两项检查的 passed 均为 false；
   - name、status_check.expected、field_check.field、
     field_check.expected 从用例原样保留。
   该报告经 run_case（第 360-369 行）以 JSON 写入 stdout，stderr
   为空。

5. 每个用例只发送一次 GET（execute 中仅一次 connection.request，
   第 291 行），超时后不重试。

三、两个受控 127.0.0.1 示例（timeout_seconds 为 0.5）
------------------------------------------------------

两个示例的用例均沿用 cases/health.json 的名称、状态码与字段期望，
仅把 url 指向本地受控服务的临时端口，并加入 "timeout_seconds": 0.5：

  {
    "name": "health",
    "url": "http://127.0.0.1:<临时端口>/health",
    "expected_status": 200,
    "field": "status",
    "expected_value": "ok",
    "timeout_seconds": 0.5
  }

示例一：响应头等待超时
  服务行为：收到 GET 后保持连接，但不发送任何响应字节（无响应头）。
  对应 tests/test_timeout_seconds_config.py 中
  CustomTimeoutEnforcementTests.test_custom_timeout_bounds_wait_for_stalled_response
  及其 _HangingServer（该测试用例名为 "timeout-custom-half-second"，
  其余字段相同）。

示例二：正文等待超时
  服务行为：收到 GET 后立即发送 200 响应头并声明 Content-Length: 15，
  只发送正文前缀 {"status":（10 字节），随后保持连接而不补齐剩余
  5 字节。对应 tests/test_body_timeout.py 中
  CustomBodyTimeoutTests.test_incomplete_body_times_out_with_custom_timeout
  及其 _PartialBodyServer("stall")。

两个示例的共同结果（可逐项核对）：
  - 命令在约 0.5 秒后超时结束（测试接受 0.3 至 2 秒的等待窗口；
    若实现忽略配置回退到三秒，等待会超过两秒而被发现）；
  - 退出码为 1；
  - stderr 为空，不出现 Traceback；
  - stdout 有且仅有一个 JSON 报告，内容形如：

      {
        "name": "health",
        "passed": false,
        "error": "request_failed",
        "status_check": {"expected": 200, "actual": null, "passed": false},
        "field_check": {
          "field": "status",
          "expected": "ok",
          "actual": null,
          "passed": false,
          "present": null
        }
      }

    （示例一的测试用例名为 "timeout-custom-half-second"，其报告
    name 相应为该值；字段名与期望值同样原样保留。）
  - 服务各只收到一次 GET，超时后没有重试。

注意示例二的含义：尽管服务已发出 200 状态码，正文未收满即超时，
报告仍是 request_failed，status_check.actual 为 null 而非 200——
即上节第 3 点：不会用已收到的状态码先生成成功检查。

四、对应测试索引
----------------

- tests/test_timeout_seconds_config.py
  - AcceptedTimeoutTests：省略时保持 3.0 秒；0.1、30、1、0.5 均被
    接受，load_case 返回的 timeout_seconds 为对应 float。
  - RejectedTimeoutTests：true、false、"1"、null、[]、{}、0、-1、
    -0.5、0.09、30.1、NaN、±Infinity 全部被 load_case 以 CaseError
    拒绝；子进程层面退出码 2、stdout 为空、stderr 以
    "api_workbench:" 开头且含 "timeout_seconds"、无 Traceback，
    服务收到请求数为零。
  - CustomTimeoutEnforcementTests：示例一（响应头等待超时）。
- tests/test_body_timeout.py
  - CustomBodyTimeoutTests.
    test_incomplete_body_times_out_with_custom_timeout：
    示例二（正文等待超时）。
  - 同文件 test_completed_body_after_short_delay_passes 为成功对照：
    前缀发出 0.1 秒后补齐正文（仍在 0.5 秒超时内），退出码 0、
    error 为 null、两项 actual 分别为 200 与 "ok"、present 为 true，
    进一步说明超时约束的是每次阻塞等待而非整次执行。
